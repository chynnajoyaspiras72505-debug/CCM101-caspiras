# Mission Reflection

Checking the host server's resources is important even when containers appear to be running perfectly because the host provides the CPU, memory, and disk resources that containers depend on. A container may be healthy while the host is running low on memory or storage, which can eventually cause performance problems or service failures. Establishing a baseline helps identify unusual resource usage before it becomes a serious issue.

If a user complains that they cannot log into a web application, the docker logs command can help by showing the requests, responses, and errors generated by the application. I can inspect the logs for HTTP errors, failed requests, or other messages that may explain why the login is not working. This provides evidence instead of relying only on assumptions.

Monitoring logs and monitoring metrics provide different types of information. Logs show detailed events and application activity, such as successful requests and the HTTP 404 error generated during this mission. Metrics show numerical resource information such as CPU usage, memory usage, network traffic, and other container performance data.

Large enterprise companies can monitor thousands of containers using centralized monitoring and observability tools such as Prometheus and Grafana. These tools can collect metrics from many systems and present them through dashboards and alerts, allowing engineers to identify problems quickly across a large infrastructure.

My ability to troubleshoot Linux environments has improved because I am now more comfortable using command-line tools to inspect system resources, processes, Docker containers, logs, and performance metrics. I learned how to connect these outputs to actual application behavior and use the information as evidence when diagnosing problems. This mission helped me understand that cloud operations is not only about deploying applications but also about continuously monitoring their health and performance.
